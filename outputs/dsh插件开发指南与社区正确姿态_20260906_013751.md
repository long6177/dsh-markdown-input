# DSH 插件开发指南与社区「正确姿态」

## TL;DR

DeepSeek Harness（`dsh`）是 DeepSeek 开源的 Agent 框架，**一切皆插件**（底层是 Cordis 框架）。目前处于 **developer preview**，官方核心仓库**暂不接受外部 PR**，官方明确把贡献路径指向**插件生态**。所以你的正确路线是：**独立仓库开发插件 → 打上 `dsh-plugin` GitHub topic（官方白纸黑字要求的发现机制）→ 提交进 awesome 精选列表 → 在 Discussions 分享/反馈**。

## 一、官方对「贡献」的定义（CONTRIBUTING.md 原文精神）

这是你所有社区动作的总纲：

- **暂时不接受外部 Pull Request**，报 bug、提功能建议都走 [GitHub Discussions](https://github.com/deepseek-ai/deepseek-harness/discussions)，并可以通过 **upvote** 别人的讨论来帮小团队排优先级。
- **生态贡献被官方认为是平等甚至更受鼓励的一等公民路径**：写插件、写教程博客、在社区答疑。
- 原话：「我们不认为官方仓库里的包天然比社区创建的包更重要。你可以把这个仓库当作一个想法、一个官方展示柜和灵感来源，而不是我们的强制命令。」
- 官方 README 明确要求：**给你的插件仓库添加 [`dsh-plugin`](https://github.com/topics/dsh-plugin) topic**，这是整个插件生态的发现机制——awesome 列表爬虫就是靠扫这个 topic 收录插件的。
- 另有官方 Discord 社区。

## 二、技术主线：插件开发六步流程

### 第 1 步：搭环境

- Node `^22.19.0 || >=24.0.0`，pnpm（仓库锁定 `pnpm@11.7.0`，建议 `corepack enable`）。
- `git clone https://github.com/deepseek-ai/deepseek-harness.git && pnpm install && pnpm run typecheck`（typecheck 通过即搭建完成；真实跑模型需要 `DEEPSEEK_API_KEY`，放根目录 `.env`）。不想克隆源码也可以 `npx @deepseek-ai/dsh web` 直接体验。
- 官方教程在 `docs/user/develop/`（文档站 [develop/basic](https://deepseek-harness.github.io/deepseek-harness/develop/basic/)），共约 9 篇：第一个插件 → 写一个工具 → 插件配置 → 打包与安装 → Cordis 框架教程；参考手册另有 [扩展形态实操手册](https://deepseek-harness.github.io/deepseek-harness/reference/cookbook/extension-cookbook)（功能→扩展点映射表，很有用）。仓库还有 `AGENTS.md`，如果你用 AI agent 参与开发，先读它。

### 第 2 步：理解插件模型（30 分钟概念）

一个插件 = 一个导出四个东西的**纯 ESM** TypeScript/JS 模块：

```js
import type { Context } from '@deepseek-ai/cordis'

export const name = 'my-plugin'        // 插件唯一 id，patch 用它定位
export const inject = ['tools']        // 声明必需服务，loader 等服务就绪才执行 apply（加载顺序由依赖决定，不是文件顺序）
export function apply(ctx, config) {   // 入口：通过 ctx 注册能力
  ctx.tools.register(/* defineTool(...) */)
}
// 还有可选导出：Config（Schemastery schema，提供校验与默认值）
```

- 三种形态：**函数**（绝大多数场景够用）、**对象**、**类**（只有当你要向其他插件提供服务时才用类）。
- **注册即可逆**：所有经 `ctx` 注册的监听器/工具/定时器在插件卸载时自动清理；自有资源用 `ctx.effect(() => { ...; return cleanup })` 包裹。
- 可选服务用 `ctx.get('xxx')` 探测，不要写进 `inject`。

### 第 3 步：本地开发循环（--patch 覆盖层，免打包）

在仓库 checkout 根目录建 `scratch-plugin/src/my-plugin.ts` + `cordis.yml`：

```yaml
- insert:
    - id: hello
      name: '/absolute/path/to/deepseek-harness/scratch-plugin/src/my-plugin.ts'  # 必须绝对路径
```

```sh
pnpm dsh web --patch ./scratch-plugin/cordis.yml   # 打开 http://127.0.0.1:3080 验证
```

无 key 验证：`dsh --profile headless --dump-config | grep <插件id>` 确认配置真的进了插件树。

### 第 4 步：选对扩展点（决定你的插件长什么样）

| 你想做的事 | 扩展点 |
|---|---|
| 给模型加能力（最常见） | `ctx.tools.register()` + `defineTool()`（schema 自动流入 prompt 组装） |
| 注入规范/拦截行为 | 事件：`agent/pre-step`、`tools/pre-execute`（可拒绝调用）、`tools/post-execute`（观察必须调 `next()`）、`turn/end` |
| 注册技能 | `ctx.get('skills')` 可选注册 runtime skill（Markdown 说明书，按需注入不占常驻 token） |
| Web UI 界面 | UI 插件：监听 `session/event` 渲染、注册 `ConversationNodeDefinition` + keyed Chat renderer、`ctx.slots.register` 面板 |
| 接入新模型 | `registerAdapter` 注册 `LlmAdapter` 子类 |
| 接入已有 MCP/Claude Code hooks | 也可走桥接，但官方定位：原生 cordis 插件「能做到桥做的一切，而且更强」——**能用原生就用原生** |

选择原则（社区精读文章总结）：要改模型看到的消息、要拦截执行、要类型安全 → **原生插件**；能力是独立服务或非 TS 生态 → MCP。

### 第 5 步：打包成可安装的 bundle

`package.json` 是关键，社区 awesome 列表甚至以**是否声明 `dsh.bundle` manifest** 作为「真插件」的硬性验证标准：

```jsonc
{
  "name": "dsh-markdown-input",
  "type": "module",                        // 必须纯 ESM
  "main": "lib/index.js",
  "files": ["lib", "cordis.patch.yml"],
  "keywords": ["dsh-plugin", "deepseek-harness"],   // 加上关键词
  "peerDependencies": { "@deepseek-ai/cordis": "*" }, // cordis 只 import type，运行时 ctx 由宿主传入
  "dependencies": { "@deepseek-ai/dsh-tools": "^0.1.0-rc.x" }, // 锁 next tag 版本线！
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

```yaml
# cordis.patch.yml —— name 填包名，不是路径
- insert:
    - id: markdown-input
      name: dsh-markdown-input
```

**版本坑（社区反复踩）**：npm 上 `@deepseek-ai/dsh-tools` 的 `latest` tag 是过期的 `0.0.1-rc.1`，真版本线在 `next` tag；所有 `@deepseek-ai/dsh-*` 依赖保持同一 `0.1.0-rc.x` 线，避免 pnpm 装出两份。

### 第 6 步：安装、发布、收录

```sh
# 安装（三种来源；dsh plugin 实质是转发给 profile 目录里的 pnpm，需要装 pnpm）
dsh plugin --profile web add dsh-markdown-input          # npm（推荐：预构建产物，一次成功）
dsh plugin --profile web add github:you/dsh-markdown-input # git 源码：需要包提供自包含的 prepare 构建脚本，且用户要授权 pnpm allowBuilds（供应链考量，官方建议锁 commit）
dsh plugin --profile web add link:/path/to/plugin          # 本地开发
```

分发优先级：**npm 发布（预构建）> tarball（`pnpm pack`）> git 源码**（后两者不麻烦用户授权构建）。

## 三、社区「正确姿态」清单

**仓库层（回答你的 dsh-plugin 标签问题）**
1. GitHub 仓库 topics 加 `dsh-plugin`（官方要求，生态爬虫靠它）——`gh repo edit --add-topic dsh-plugin`；顺手加 `deepseek-harness`、`cordis`、`dsh`。
2. `package.json` 的 `keywords` 同步带 `dsh-plugin`。
3. 必须有有效的 `dsh.bundle` manifest，否则 awesome 列表只把你归入「相关项目」而非「插件」。
4. MIT 协议 + 双语 README 是社区主流（国内社区活跃，中英双语收益明显）。

**行为层**
5. **不往核心仓库提 PR**；bug/建议走 Discussions，好想法先发讨论再动手。
6. 完成后去 Discussions 的 **"Show Your Plugins!"** 分类发帖（ciceroyang 的 #961 就是模板），再给 [awesome-dsh-plugin](https://github.com/awesome-dsh-plugin/awesome-dsh-plugin)（110★ 精选列表，PR 收录，没有合适类目可以提案新类目）和 [dsh-suite](https://github.com/whyihaveyou/dsh-suite)（活目录：每小时刷新、每日兼容实测、还带 Web UI 内置插件商店）提收录 PR。
7. 可以用社区脚手架起步：`npm create dsh-plugin`（dsh-suite 出品，tool/events/webui 三套模板 + `--verify` 冒烟测试），或 [ciceroyang/dsh-plugin-starter](https://github.com/ciceroyang/dsh-plugin-starter)。系统性教程推荐 [DumplingHuman/dsh-plugin-tutorial](https://github.com/DumplingHuman/dsh-plugin-tutorial) 和 [whyihaveyou/dsh-plugin-tutorial](https://github.com/whyihaveyou/dsh-plugin-tutorial)（双语、15 条设计准则、14 个坑）。

**兼容性与安全层（preview 期特有）**
8. 官方明说 **"THERE WILL BE COMPATIBILITY-BREAKING CHANGES"**，AGENTS.md 还写了 pre-release 期间「宁要正确地基不要兼容垫片」——意味着你的插件要跟着上游快速重测。`@deepseek-ai/cordis` 必须是 peerDependency（装成普通依赖会出现第二份实例，服务注册表对不上，插件永远激活不了——这是最隐蔽的坑）。
9. 遥测/日志会带出完整会话内容，涉及用户数据的插件要自己做脱敏（社区审计插件的成熟做法）。
10. git 分发注意：pnpm ≥10 默认拦截 install 脚本，作为作者要提供 `prepare` 脚本，作为用户只对可信源码授权并锁 commit。

## 四、对你 `dsh-markdown-input` 的落地建议

你的目录还是空的。如果插件的核心是「让模型输出/处理 Markdown」→ 走 **tool + skill** 路线（最简单，纯宿主侧）；如果是「改进用户输入 Markdown 的界面体验」→ 那是 **UI 插件**，需要宿主/浏览器双半结构（`ctx.slots.register` + 浏览器 bundle），复杂度高一档，建议先用 `npm create dsh-plugin` 的 webui 模板起步。无论哪种，第一步都是把 dsh 源码跑起来、照官方「第一个插件」教程走通 `--patch` 循环。
