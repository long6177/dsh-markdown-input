# npm 首发 + 官方桌面端安装体验的远程反馈闭环

v1 的效果验证依赖开发机本机直装测试，测试残留与迭代耦合在开发环境里。v2 起改为远程闭环：插件以 `dsh-plugin` 生态元数据发布到 npm，用户在官方桌面端（0.2.0-rc.2 内核）的插件管理 UI 中直接搜索安装、日常体验，以口头反馈驱动迭代；开发机不再承担效果测试。npm 包名遵循先到先得，安装入口应尽早建立并保持稳定，因此发布动作前置于 MVP 完成——`0.2.0-alpha.0` 由现有代码发布，仅用于验证发布管线与确定包名，不做推广；MVP 功能由 `0.2.0-alpha.1` 交付并伴随生态收录动作。

## Considered Options

- **GitHub 源分发**：拒绝为主通道。用户侧需授权 pnpm 构建脚本，安装体验差，官方亦仅列为第三优先；保留为 npm 不可用时的备胎。
- **继续本机直装测试**：拒绝。与开发环境耦合，且违背本次「不在本机环境做效果测试」的约定。
- **MVP 完成后一次性首发**：拒绝。npm 包名先到先得，延后发布使安装入口暴露于不确定窗口。

## Consequences

- 版本线 `0.2.0-alpha.x`；`peerDependencies` 声明兼容 `@deepseek-ai/dsh` 内核包的 `0.2.0-rc.x` 线（以 `^0.2.0-rc.2` 起计），内核据此在插件管理页识别或跳过不兼容版本并给出原因。
- 发布执行：仓库维护者本机保持 npm 登录态，发布命令由开发流程代跑、OTP 由维护者输入；凭据不经手第三方。
- 每次发版附带一份验收清单（≤8 条），作为用户真机口头反馈的对照基准；反馈由维护者口头给出、开发侧记录并转化为迭代。
- MVP 版本发布时同步完成生态发现动作：仓库 topics 补 `dsh-plugin`、向 awesome 列表提收录 PR、在官方 Discussions 发布介绍帖；所有公开文案仅描述产品自身能力。
- 开发依赖模型见 [ADR-0007](0007-dev-deps-published-packages-with-fidelity-mode.md)：本仓测试默认跑发布包、保真模式指回上游 checkout；发布前全量在保真模式下对准上游 tag 执行，真机重测环节不变。
